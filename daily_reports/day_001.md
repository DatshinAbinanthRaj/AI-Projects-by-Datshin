### 2. What Did We Build?

A command-line tool that reads a Bar Bending Schedule and sorts every row into one of four piles: accept automatically, send back to the detailer with a suggested fix, send to a human reviewer, or pick as a random spot check. It stores what the reviewer decided and then reports how good the automated checks were.

### 3. Why Is This Project Important?

Any QA process has to decide what a machine can judge and what needs a person. If everything goes to people, it is slow and expensive. If everything is automated, wrong items slip through and nobody knows. A rebar checker has this problem, and so does an annotation or LLM-evaluation pipeline. QA leads, human data managers and checking engineers all need the same three things: a routing rule, an audit trail, and numbers that show whether the automation can be trusted.

### 4. How Does It Work?

1. `check` reads the CSV and runs nine checks on each row.
2. Each finding is marked **certain** (arithmetic, fixed rule) or **needs judgement**.
3. Rows are routed: no findings = auto-accept; only certain errors = auto-flag; any judgement finding = human review.
4. 10 % of the auto-accepted rows are randomly pulled out as a QA sample for a human.
5. The reviewer records `issue` or `ok` for each queued row.
6. `report` calculates the automation rate, the false-alarm rate per rule and the escape rate.

Example: a 16 mm straight bar, 2 members x 5 bars, 4000 mm long.
- Total bars written as 12: certain error, auto-flagged, suggested value 10.
- Cut length written as 4050: only 50 mm off, could be an allowance, so it goes to a human.
- Cut length written as 4500: 500 mm off, certain error, auto-flagged.

### 5. What Technologies Were Used?

- **Python standard library**: no installation needed, so anyone can run it.

- **random with a seed**: makes the QA sample and the synthetic data reproducible.
- **pytest**: runs the 28 automated tests.

### 7. What Were the Results?

- Sample run on 60 synthetic rows: 28 auto-accepted, 18 auto-flagged, 11 human review, 3 QA sample. 76.7 % of rows needed no human.
- Simulated reviewer: 5 of 11 human-review rows confirmed as issues, 6 cleared. 0 of 3 sampled clean rows had a defect.
- All 23 injected defect rows were caught and no clean row was auto-flagged.
- Tests: 28 executed, 28 passed.
- Limits on these numbers: the defects were injected by the same project that detects them, and the reviewer decisions were simulated from the ground truth. They show the workflow works, not how accurate it would be on a real schedule.
- Other limitations: four shape codes, illustrative thresholds, CSV only, one reviewer per row.

### 10. Interview Explanation — 90 Seconds

**Problem.** Checking a bar bending schedule fully by hand is slow, and fully by script is risky, because some deviations are judgement calls. AI data pipelines have the same problem with labels and model outputs.

**Approach.** I split findings into certain and needs-judgement, and route each row to auto-accept, auto-flag or human review. I added a random QA sample of accepted rows, because that is the only way to see what the rules miss.

**Implementation.** Python with the standard library. The checks are pure functions. Routing and the decision log use SQLite, and decisions are append-only so there is an audit trail. Everything runs from the command line.

**Validation.** I generated a synthetic schedule with known injected defects and wrote 28 tests. On the sample file all injected defects were caught and no clean row was wrongly flagged.

**Outcome.** About three quarters of the sample rows needed no human, and the report shows the false-alarm rate per rule, which tells you which threshold to adjust. The limits are clear: the data is synthetic and the reviewer was simulated, so it proves the workflow, not real-world accuracy.

### 11. Five Likely Interview Questions

**1. How did you decide what goes to a human?**
By the type of rule, not by a score. Arithmetic checks (total bars = members x bars per member) are either right or wrong, so they are "certain". A cut length 50 mm off could be rounding, an allowance or a mistake, so that rule is "needs judgement". Any row with one judgement finding goes to a human.

**2. Why sample rows that passed every check?**
Rules only catch what they were written for. A QA sample (here 10 % of clean rows) lets a human look for anything else. The share of sampled rows with a problem is the *escape rate*: an estimate of defects getting through the automation.

**3. What is a false-alarm rate and why track it per rule?**
It is the share of flagged items the reviewer said were fine. In the sample, the small-length-deviation rule had 4 false alarms out of 7. That tells me this rule creates most of the unnecessary review work, so its threshold is the first one to tune.

**4. How do you know the tool is correct?**
Two ways: unit tests with hand-calculated values, and a synthetic dataset where I know exactly which rows are broken. I am careful about what that proves. Detecting defects I injected myself shows the code works as designed; it does not measure accuracy on real schedules. For that I would need real, independently checked data.

**5. How would you scale this to a team of reviewers?**
Assign queue items to reviewers, have a share of items reviewed twice to measure agreement, add an adjudicator for disagreements, and track throughput and accuracy per reviewer. The decision table already stores reviewer name and time, so those reports can be built on it.

### 14. What Should I Learn?

1. **Escape rate and QA sampling**: checking a random share of accepted items to estimate how many defects pass unnoticed. Be ready to explain why 3 sampled rows is far too few to trust the 0 % figure.
2. **Precision vs recall**: recall is the share of real defects caught; precision is the share of flags that were real. The false-alarm rate is 1 minus precision.
3. **Pure functions and unit tests**: `checks.py` has no file or database access, which is why each rule can be tested with one line. Open `tests/test_rebar_qa.py` and read five tests.

Practise yourself: run the six commands in the README, change one value in `sample_bbs.csv`, and see which route the row moves to.
